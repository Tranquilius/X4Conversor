# X4Conversor

A 100% static web app that converts PDFs and TXTs into clean TXT/EPUB files for the **Xteink X4**
e-ink reader. All processing happens in the browser — no file is ever uploaded to a server.
Published on GitHub Pages.

## The problem it solves

PDF text extractors often decide where word boundaries are by comparing the horizontal distance
between glyphs against a fixed threshold. When the declared width of a wide glyph (typically `m`)
is wrong in the embedded font's `Widths` table, this produces systematic ghost spaces:
`"ela estava m orta"` instead of `"ela estava morta"`.

This tool attacks the problem on two fronts:

1. **PDF**: reconstructs words from the actual glyph geometry (x/y position, width), with an
   adaptive threshold (Otsu) computed per font from every gap in the document — never a fixed
   threshold. This avoids the bug at the source.
2. **Already-corrupted TXT**: the geometry no longer exists, so the repair is lexical and
   best-effort (pipeline stage 7 — see `src/pipeline/07-ghost-space/`), with statistical
   diagnostics, confidence bands, and user review for the ambiguous cases.

Note: the tool repairs **Portuguese (PT-BR)** text specifically — the lexicon, the character
statistics, and the chapter-detection patterns are all tuned for Portuguese, since that is the
actual target of this converter. The app's own interface is in English.

## Running locally

Requires Node.js 20+.

```bash
npm install
npm run build:lexicon   # generates public/lexicon/pt_br.json from data/lexicon-src/ (see below)
npm run dev              # http://localhost:5173/X4Conversor/
```

Other scripts:

```bash
npm run typecheck   # tsc --noEmit
npm test             # vitest (pipeline stages)
npm run test:e2e     # playwright (full UI flow)
npm run build         # production build into dist/
npm run preview       # serve dist/ locally
```

## Deploying to GitHub Pages

The `.github/workflows/deploy.yml` workflow builds and publishes automatically on every push to
`main` (it runs the tests first; only publishes if they pass). To enable it:

1. On GitHub, go to **Settings → Pages** and select **Source: GitHub Actions**.
2. Confirm that `vite.config.ts` has `base: '/X4Conversor/'` matching your repository name exactly
   (GitHub Pages serves at `user.github.io/X4Conversor/`, with the same casing as the repo —
   adjust this value if your repository has a different name).
3. Push to `main`.

To run it manually: **Actions** tab → **Deploy to GitHub Pages** workflow → **Run workflow**.

## Architecture

A 9-stage pipeline, each a pure function `(input, options) => {output, stats}` testable in
isolation (`src/pipeline/`):

1. **Ingestion** (`01-ingest.ts`) — encoding detection (strict UTF-8 → mojibake heuristic →
   windows-1252 fallback), BOM removal.
2. **Geometric extraction** (`02-geometry.ts`, PDF only) — via `pdfjs-dist`, with an adaptive
   per-font threshold (`src/util/otsu.ts`) for word reconstruction. Also extracts the PDF outline.
3. **Character cleanup** (`03-charclean.ts`) — NFC, ligatures, invisible characters, NBSP.
4. **Header/footer removal** (`04-headers-footers.ts`, PDF only) — lines repeated on ≥60% of
   pages in the same y range, isolated page numbers.
5. **De-hyphenation** (`05-dehyphenate.ts`) — consults the lexicon to keep the hyphen in compound
   words (`guarda-chuva`).
6. **Paragraph reflow** (`06-reflow.ts`) — joins physical lines into the same paragraph.
7. **Ghost-space repair** (`07-ghost-space/`) — the core. Phase A (statistical diagnostics) →
   B (candidate generation) → C (confidence bands) → D (grouping for batch review in the UI).
8. **Chapter detection** (`08-chapters.ts`) — the PDF outline as priority 1, a short-heading
   heuristic as priority 2. Editable in the UI before exporting.
9. **Export** (`09-export-*.ts`) — TXT (configurable BOM/EOL), EPUB (JSZip, `mimetype` first/
   uncompressed), an HTML change report. EPUB export has an "Optimize for e-ink readers (Xteink
   X4)" toggle (on by default), which swaps in a CSS profile using longhand `margin-*` and
   percentage side insets — the X4's built-in reader has been reported to drop shorthand `margin`
   declarations and indentation, leaving body text with no visible side margin.

All heavy processing runs in a **Web Worker** (`src/worker/pipeline.worker.ts`), split into two
phases: `extractAndReflow` (expensive — includes PDF parsing) and `finalizeDocument` (cheap —
reapplies stage 7/8), so reviewing phase D or editing chapters never has to reprocess the whole PDF.

## Lexicon: sources and licenses

`public/lexicon/pt_br.json` is generated by `npm run build:lexicon` (`scripts/build-lexicon.mjs`)
from two sources in `data/lexicon-src/` (not version-controlled — re-download before running the
script; see the URLs in the script itself):

- **[hermitdave/FrequencyWords](https://github.com/hermitdave/FrequencyWords)**,
  `content/2016/pt_br/pt_br_50k.txt` — the 40,000 most frequent Portuguese words, with occurrence
  counts. Used for: word validity, frequency ranking, and stage 7's `intra[c]`/`before[c]`
  reference table (derived from the lexicon's own words, not a separate running-text corpus).
  **License: code MIT; data CC-BY-SA-4.0** (derived from OpenSubtitles/OPUS subtitles).
  CC-BY-SA-4.0 requires attribution and share-alike — this license notice is that attribution, and
  the generated `public/lexicon/pt_br.json` inherits the same terms for the part derived from
  this source.

- **LibreOffice's Hunspell pt-BR dictionary** (the VERO project, Raimundo Moura and team),
  [`LibreOffice/dictionaries`](https://github.com/LibreOffice/dictionaries), `pt_BR/` folder
  (`pt_BR.dic`) — used only for **additional validity** (words not among the top 40k by
  frequency, including hyphenated compounds like `guarda-chuva` and `mal-estar`, which stage 5
  consults to decide whether to keep the hyphen). **License: LGPLv3 or MPL** (dual license).

  **Documented limitation:** we only use the root words from the `.dic`, without expanding the
  `.aff` affix rules (which would require a full Hunspell expander). This means some inflected
  forms that only exist via an affix rule (not as a root word and not among the top 40k by
  frequency) are not recognized as valid. In practice, the combined coverage of both sources is
  already broad.

You can also load an extra per-book word list from the UI (fictional proper nouns) — these feed
into phase C's "local document lexicon", with the same protective effect that proper nouns
repeated 3+ times already get automatically.

## Known limitations (v1)

- **Empty bigram model by default.** Stage 7's band 2 (ambiguous cases like `"com o"` ↔
  `"como"`) has no real bigram corpus built in — by design, when that data is unavailable, the
  algorithm sends the case to the review queue instead of deciding on its own (this is what
  prevents the false positive of turning `"ele saiu com o irmão"` into `"...como irmão"`). The
  architecture (`src/pipeline/07-ghost-space/bigram-model.ts`) is already set up to receive a real
  model in the future.
- **No Hunspell affix expansion**, see section above.
- **One file processed at a time**, sequentially, when multiple are dropped at once.
- **No `.xtc` generation** (pre-rendered bitmaps) — out of scope for v1; this tool's clean EPUB
  output feeds converters like `bigbag/epub-to-xtc-converter`.
- **No OCR** — PDFs with no text layer are detected and the user is told to run `ocrmypdf` first.
- **E2E coverage**: the Playwright test (`tests/e2e/convert-flow.spec.ts`) uses a TXT fixture
  (simpler to maintain than generating a synthetic PDF); the PDF-specific geometric reconstruction
  has its own coverage in `tests/unit/geometry.test.ts`, including the exact bug scenario (wrong
  declared width for `m`) via a simulated PDF document.

## Tests

```bash
npm test          # 9 files, ~35 cases — every pipeline stage
npm run test:e2e   # full flow: drop a file → review → export → check the download
```

Covered cases include the 8 examples from the original problem statement, a false-positive
regression test (`"com o irmão"` never becomes `"como irmão"`), hyphen preservation in compound
words, proper nouns surviving intact, a clean document coming out identical, byte-for-byte
determinism, and structural EPUB validity (`mimetype` first/uncompressed/exact content).
